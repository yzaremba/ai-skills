## How actions are done on Claude Code

Read against the docs of Claude Code 2.1.289; not run. Role ids are used as written: `product-manager`, `coder`, `coder-hard`.

- **Dispatch a role.** Call the `Agent` tool with `subagent_type` set to the role id and the brief as `prompt`. The agent starts with a fresh context; the brief is all it has of yours. Pass no `model`: the definition pins model and effort, and a `model` on the call would override the pin. Pass a `name` equal to the role id plus a short suffix, so the agent can be addressed later. The hard Coder is `coder-hard`.
- **Wait for a dispatched agent.** It usually runs in the background. Its output arrives later as a completion notification marked as that agent's. That is agent output, never the user. Until it arrives the agent is still running; do not guess its result.
- **Follow up with a finished agent.** Call `SendMessage` with `to` set to the agent's name or the agent id its result gave you. It resumes with its whole history. Dispatching again would start a new agent that knows nothing. After a restart this works only once the same session has been resumed.
- **Dialogue with the user: the user can type to a dispatched agent.** So the Manager dispatches the Product Manager for dialogue and tells the user: while the agent runs, select its row in the agent panel under the prompt, press Enter to open its transcript, and type there. An open transcript stays open when the turn ends. A finished agent's row is removed at once; for 30 seconds `/tasks` still lists it, and Enter on it there opens the transcript. After that, the user asks you, and you follow up with the agent, which resumes it. What the user types there does not reach you; you get only what the agent reports. Whether a turn the user drives there sends you a completion notification is not documented, so act only on what reaches you. If the user returns and says the agent is done and no hand-back has arrived, follow up with the agent and ask for its hand-back.
- **If you are the dispatched agent in a dialogue.** You have no question dialog. Write the question as plain text in your thread first, then hand back; the hand-back ends the turn. If a tool is given to you for the final report, the hand-back is that call and the question is still written before it. The user answers in your thread, which resumes you.
- **Load a role.** Needed here only when the user asks for it. The user types `/<role-id>`, where that role is installed as a skill. You do not load a role yourself.
- **Switch the loaded role back.** There is no command. The user says it in a message, such as "back to the Manager", and it holds from that message on.
- **Start a session as a role.** The user runs `claude --agent manager`, or the project's `.claude/settings.json` sets `"agent": "manager"`. The startup header then shows `@manager`. You cannot do this from inside a session.
- **Nesting.** Agents nest three layers below the main session. An agent at the limit has no `Agent` tool and does the work itself.
- **Run a command.** The `Bash` tool. A permission prompt goes to the user; another agent's message never answers one.
- **Change a file.** `Edit` for an existing file, `Write` for a new one. A role that may not change files also does not change them through `Bash`.
- **Commit.** With `Bash`: `git add -- <new file>` for each file git does not track yet, never `git add -A`, `git add .` or `git commit -a`; then `git commit -m "<message>" -- <file> <file>` naming every file of the change, new ones included, which commits those files only and leaves out anything staged before; then `git log -1 --oneline` and report that id. Use `git -C <dir>` when the brief's working directory is not the current one.
- **Confirm a commit exists.** `git log -1 --stat` in the brief's working directory.
