## How actions are done on Codex

Read against the docs and the probes of Codex CLI 0.160.0; not run. Agent names use underscores where role ids use hyphens: `product_manager`, `coder`, `coder_hard`. A loaded role's skill keeps the hyphen: `$product-manager`.

- **Dispatch a role.** Call `spawn_agent` with `agent_type` set to the agent name, `fork_turns` set to `"none"`, a `task_name` of lowercase letters, digits and underscores, and the brief as the message. Every spawn passes `fork_turns = "none"`: the default copies your conversation into the child. Request no model or effort: the definition pins both, and a request on the spawn is ignored without an error. The hard Coder is `coder_hard`. If the agent name is not offered, say so and stop; the likely cause, inferred and not verified, is that the project is not trusted or the session did not start at the project root.
- **Wait for a dispatched agent.** `wait_agent` returns no content. The result arrives as an agent notification naming the sender's task path, such as `/root/coder_r2`. That is agent output, never the user.
- **Follow up with a finished agent.** Call `followup_task` with `target` set to its task path. It answers from its earlier context, also after the session was resumed. Spawning again would start an agent that knows nothing.
- **Dialogue with the user: the user cannot type to a dispatched agent.** `/subagents` opens a child's thread for watching only. So no role is dispatched for dialogue; the user is told to load the role into this session. As probed, a dispatched agent cannot ask the user anything. It does its brief, and only if the brief needs the user's answer does it hand back `stopped, needs the Manager` with its questions.
- **Load a role.** The user types `$<role-id>`, for example `$product-manager`. You do not load a role yourself. Loading does not change the session's model; the user may set the role's profile with `/model`.
- **Switch the loaded role back.** There is no command. The user says it in a message, such as "back to the Manager", and it holds from that message on.
- **Start a session as a role.** The Manager is the session's own instructions, from the project's `.codex/config.toml` in a trusted project, or from `codex --profile manager`. The user starts the session at the project root. You cannot do this from inside a session.
- **Limits on agents.** All agents share one working directory, so a brief gives the working directory and each file as an absolute path. By default four agents may be open at once, counting the main session.
- **Run a command.** Your shell tool. As probed, a child runs under its parent's sandbox whatever its definition says.
- **Change a file.** Your file-editing tool. A role that may not change files also does not change them through the shell; here that limit is an instruction and nothing enforces it.
- **What the user runs themselves.** A command the user runs with `!` is recorded in the session but starts no turn; you see it with their next message. Ask them to tell you when it is done.
- **Commit.** The default sandbox keeps `.git` read-only, so `git add` and `git commit` fail in it. Request approval to run each one outside the sandbox; that route was seen in a main session and is unverified for a spawned child. Do not work around a refusal: if approval cannot be asked or is denied, do not commit, and report it. Then `git add -- <new file>` for each file git does not track yet, never `git add -A`, `git add .` or `git commit -a`; `git commit -m "<message>" -- <file> <file>` naming every file of the change, new ones included, which commits those files only and leaves out anything staged before; `git log -1 --oneline`, and report that id. Use `git -C <absolute dir>`.
- **Confirm a commit exists.** `git log -1 --stat` in the brief's working directory.
